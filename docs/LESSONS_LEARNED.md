# Lessons Learned

## 2026-09 · OCR / GetNote / Book Router

这轮迭代的核心结论不是“把 OCR 做得更复杂”，而是重新确认产品主线：

> 把别人推荐给我的书，低摩擦地送进我真正使用的阅读系统。

对应主流程：

```text
Capture
↓
Book Resolution
↓
Douban Want-to-Read
↓
WeRead Availability
```

而不是去做一个新的收藏工具、OCR 工具、知识库或 AI 推荐系统。

## 经验

1. 不要为了一个 OCR 问题，把整个产品架构越做越重。
   - 从单纯“出版社识别不出来”，一路容易扩张到多区域 OCR、封面裁图、fallback、GetNote、Claude、Skill、OpenAPI、Watcher。
   - 每增加一个工具，就会增加授权、状态、延迟和排错成本。

2. 先认书，再认版本。
   - 整图 OCR 只负责识别是哪本书。
   - 只有豆瓣出现多个版本时，才进入 Edition Resolution，读取出版社、ISBN、年份等版本级证据。

3. OCR 不是核心产品能力，版本解析和路由才是。
   - OCR 应该是可替换输入层。
   - 真正的价值是：识别书 → 找对豆瓣版本 → 保留正确阅读状态 / 标记想读 → 查询微信读书可读性。

4. 强证据自动化，弱证据 fail closed。

```text
ISBN
↓
书名 + 出版社
↓
书名 + 出版年份
↓
书名 + 作者
↓
只有书名
```

   - ISBN / 出版社属于版本级强证据。
   - 书名 + 作者通常不足以区分同一 Work 的不同 Edition。
   - 证据不足时宁可让用户选一次，也不要猜错。

5. 社媒截图和纯书封面是两个难度等级。
   - B站、小红书等截图含有字幕、评论、弹幕、广告和 UI 文案。
   - 社媒长句即使带《》也不能直接当作有效书名。
   - 单图识别和多图批量流程需要明确分开。

6. 性能比理论上的识别率更重要。
   - 一张图跑多次 OCR 虽可能提高召回，但会显著放大延迟和噪声。
   - 约 2 分钟才回复的能力，即使最终“能识别”，对 C 端体验也不可接受。
   - 目标应是几秒到十几秒级、稳定、少误判。

7. Detail OCR 只能用于 Edition Resolution。
   - 放大的局部 OCR 结果不能重新送回 Book Mention Extractor。
   - 否则评论、字幕和封面噪声可能生成“第二本假书”。

8. 外部服务接入前先做 smoke test，不要直接重构主流程。
   - GetNote / 得到大脑可以作为 Capture / OCR / 图片理解能力进行验证。
   - 只有当真实截图 benchmark 在出版社 / ISBN 识别和延迟上明显更好时，才考虑接入运行时。
   - 不因为“技术上能接”就立即增加同步链路。

9. 不要把 Claude、GetNote、飞书、douban-weread 全串成一条长链。
   - 用户真正需要的是：看到一本书 → 丢进去 → 自动去豆瓣想读 → 告诉我微信读书能不能看。
   - 所有新方案都要用这条最短路径来判断是否值得加入。

10. 最少操作比技术上最完整更重要。
   - 每当为了提升边缘能力，需要新增工具、新状态、新授权、新同步流程时，先问：

> 这是不是让“看到一本书 → 开始读”变得更简单？

如果答案不是明确的“是”，就先不加。

## 工程习惯

- 多次 OCR 会同时放大延迟和噪声。
- 单图与批量输入必须有独立 guard。
- 豆瓣已有“在读 / 读过”状态时不能自动降级成“想读”。
- 没有 CI 时只能说“新增了 regression tests”，不能声称测试已自动通过。
- runtime 改动需要同步并重启 LaunchAgent；docs / benchmark-only 改动不需要重启。
- 外部 Provider 应保持可替换，不要让主产品被单一第三方基础设施绑死。

## 产品判断

GetNote 可以继续作为实验性 Capture / OCR / 知识理解工具观察，但目前不应为了它增加复杂的自动同步链路。

当前最值得守住的产品定义仍然是：

> **把别人推荐给我的书，低摩擦地送进我真正使用的阅读系统。**

以及更通用的一条原则：

> **Don’t replace your system. Connect it.**
