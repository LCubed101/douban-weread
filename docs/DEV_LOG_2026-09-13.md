# Douban × WeRead 开发日记

**日期：2026-09-13**  
**版本：v0.2.0**  
**开发分支：`agent/weread-shelf-baseline`**  
**版本节点：Book Router UX**  
**今日关键词：候选污染修复 / Fail Closed / Explicit Text Fast Path**

今天没有继续扩展新的平台或新链路，而是集中处理两个更重要的问题：**搜索结果是否真的可信**，以及**确定的事情是否还需要用户多点一次**。

## 1. 修复豆瓣候选污染

测试《变量》时，豆瓣候选列表中曾混入《情绪》《变量2》《变量7》《变量8》。根因不是 OCR，也不是微信读书，而是旧流程直接把豆瓣 `search_by_title()` 的相关搜索结果当作“同一本书的版本候选”。

旧流程：

```text
输入《变量》
↓
豆瓣搜索
↓
取前几个结果
↓
全部当成版本候选
```

PR #74 增加了严格的标题过滤层：搜索负责召回，Resolver 负责判断。明确书名输入时，只保留有清晰 same-work 标题证据的结果；《情绪》《变量2》《变量7》《变量8》不再进入版本选择，也不会继续触发微信读书查询。

这一轮再次确认：

> **Search 负责召回，Resolver 负责判断。**

第三方搜索接口的排序不能直接当作最终实体匹配结果。

## 2. Explicit Text Fast Path：确定的事情少问一次

候选污染修复后，重新发送《变量》，系统已经能唯一定位：

- 书名：变量
- 作者：何帆
- 出版社：中信出版社
- 出版时间：2019-01
- ISBN：9787508698175

但旧 UX 仍然会先发一张“你想加入的是这本吗？”确认卡，需要再点一次“确认这本”，才继续检查豆瓣状态和微信读书。

PR #75 增加 Explicit Text Fast Path。仅在以下条件同时满足时跳过确认：

```text
纯文本书名
+
唯一候选
+
exact title match
+
无图书 / 影视歧义
```

现在《变量》的路径变成：

```text
发送《变量》
↓
自动检查豆瓣状态
↓
自动查询微信读书
↓
直接返回最终结果
```

真实回归已通过：不再出现多余确认卡；如果豆瓣已经是“想读”，不会重复写入；“在读 / 读过”也会保留，不降级。

## 3. 自动化没有放松安全边界

Fast Path 不是“搜到一个就自动执行”。以下情况仍然必须确认：

- 多个豆瓣版本候选
- 只有 prefix / subtitle match，而不是 exact title match
- ISBN / URL 等非纯文本书名输入
- OCR / 图片路径
- 图书 / 影视同名
- 其它证据不足或不确定情况

原则仍然是：

> **强证据自动化，弱证据 fail closed。**

优化的是确定场景的操作成本，而不是用自动化替用户猜。

## 4. 今天的产品收束

主流程进一步收束为：

```text
看到一本书
↓
告诉系统书名 / 发截图
↓
系统完成确定的动作
↓
只有真正有歧义时才打扰用户
```

产品目标从：

```text
看到 → 识别 → 必要时选一次 → 完成
```

在确定输入下进一步变成：

```text
看到 → 发出去 → 完成
```

这与项目一直坚持的方向一致：

> **把别人推荐给我的书，低摩擦地送进我真正使用的阅读系统。**

以及：

> **Don’t replace your system. Connect it.**

## 5. 版本说明

v0.2.0 标记为 **Book Router UX** 节点。

相较 v0.1.0，这一阶段重点不是增加更多平台，而是把 Book-only 主链路做得更可靠、更少误判、更少确认步骤：

- 严格过滤豆瓣搜索候选
- 保留 Edition Resolution 的 fail-closed 逻辑
- 唯一精确文本匹配时启用 Fast Path
- 保留豆瓣已有的想读 / 在读 / 读过状态
- 继续完成微信读书版本与可读性查询
